# Refactor Log

## 2025-11-09 — Публичные API для `auth` и `modal`

### Что сделано

-   Созданы файлы-ворота `src/features/auth/index.ts` и `src/features/modal/index.ts`.
-   Экспортированы только «разрешённые» артефакты (хуки, редьюсеры, компоненты), скрыты внутренние модули.
-   Обновлены импорты в `widgets/profile`, `features/checkout-form`, `features/auth`, `features/auth-btn`, `app/layout`, `store` для использования новых публичных точек входа.

### Зачем

-   Единая точка доступа к фиче упрощает поддержку и уменьшает риск «просачивания» лишней логики наружу.
-   Проще контролировать зависимости между фичами: при необходимости можно добавить фасады, не лезя в реализацию.
-   Ускоряется рефакторинг — при переносе файлов достаточно обновить экспорты в одном месте.

### Что даёт

-   Чище импорты (`@/features/auth` вместо `@/features/auth/model/...`).
-   Меньше шансов на циклические зависимости.
-   Подготовка базы, чтобы аналогично оформить остальные фичи и виджеты.

## 2025-11-09 — Наведение порядка в `search`, `filtration`, `header`, `store`

### Что сделано

-   Добавлены публичные входные точки `src/features/search/index.ts`, `src/features/filtration/index.ts`, `src/widgets/header/index.ts`.
-   Перевели `store`, `widgets/products-list`, `shared/ui`, `shared/lib/http`, `app/api` на новые импорты.
-   Внутри `filtration` убрали прямые ссылки на `@/store/index`, используем короткий `@/store`.

### Зачем

-   Выравниваем слои: у каждой фичи/виджета есть единый фасад, за счёт чего потребители не касаются внутренней структуры.
-   Снижаем связанность и упрощаем будущие перемещения файлов.
-   Чистим импорты в shared & widgets, чтобы они не зависели от глубокой вложенности конкретной фичи.

### Что даёт

-   `store` теперь собирает редьюсеры через публичные API — проще заменить или моком покрыть конкретную фичу.
-   Виджеты и shared-компоненты работают с `filtration` через фасад, не ломаются при реорганизации `model`.
-   Алиас `@/store` используется в одном виде по всему проекту — ниже риск опечаток и дублирования типов.

## 2025-11-09 — Фасады для `entities/product` и `entities/filter`

### Что сделано

-   Созданы входные точки `src/entities/filter/index.ts`. Для `entities/product` оставили публичным только слой моделей/типов, чтобы не ломать разделение server/client.
-   Обновили импорты страниц, виджетов и shared-утилит на `@/entities/product` и `@/entities/filter`.
-   Вынесли типы и схемы (`TProduct`, `Category`, `RelationKey`) в фасады, чтобы потребители не лазили по подпапкам.

### Зачем

-   Сутевые сущности теперь поставляют единый контракт, их проще переиспользовать и тестировать.
-   Снижаем связанность: фильтрация и продуктовые экраны больше не зависят от структуры `model`/`config`, при этом учитываем ограничения Next.js по импортам клиентских компонентов.
-   Подготовка к дальнейшему расширению: можно безболезненно добавлять новые файлы внутри сущностей.

### Что даёт

-   Импорт `getFiltersByCategory` стал короче и стабильнее, а клиентские компоненты подключаются напрямую из `ui`, без лишних прослоек.
-   `filtersQuery`, API-роуты и shared-helpers используют одинаковые типы `Category`, `RelationKey`.
-   Общая картина FSD стала ровнее — фасады есть у фич, виджетов и ключевых сущностей.

## 2025-11-09 — Баррели для `shared/lib` и расширение `shared/ui`

### Что сделано

-   Добавлен фасад `src/shared/lib/index.ts` и `utils/index.ts`, которые собирают ключевые утилиты (`cn`, форматтеры, product/cart utils).
-   Обновили импорты во всех UI-компонентах и виджетах на `@/shared/lib`, избавились от глубоких путей `@/shared/lib/utils/...`.
-   Расширили `src/shared/ui/index.ts`, чтобы из одного модуля приезжали основные UI-кит компоненты (Button, Breadcrumbs, SortSelect, Tooltip и т.д.).

### Зачем

-   Уменьшаем связанность с внутренней структурой shared-слоя и упрощаем работу с алиасом `@/shared`.
-   Повышаем читаемость импортов: видно, что зависимость приходит из shared-утилит или UI-кита.
-   Подготавливаем базу для дальнейшей стандартизации — можно подключать новые компоненты/утилиты, не правя десятки путей.

### Что даёт

-   Любой компонент может взять `cn`, `getProductImages`, форматтеры из одной точки.
-   Виджеты/страницы импортируют UI-кит единообразно (`@/shared/ui`).
-   Следующие реорганизации shared-слоя становятся дешевле: достаточно обновить баррель, а не все места использования.
-   Для совместимости с серверными компонентами `store` подключает `authReducer` и `modalReducer` напрямую из `model`, так как их фасады продолжают экспортировать клиентский UI.

## 2025-11-09 — Обновление `@react-three/fiber` и настройка ESLint

### Что сделано

-   Обновили `@react-three/fiber` до `8.18.0`, оставшись в ветке, совместимой с React 18.3 (версии 9.x требуют React 19).
-   Установили `eslint-plugin-prisma` и устранили выявленные линтером ошибки (комментарии в JSX, aria-атрибуты, escape символов).
-   Прогнали `npm run build`: сборка проходит, но остаётся предупреждение от `@react-three/fiber` про `unstable_act` — в ветке React 18 библиотека всё ещё пытается импортировать этот API из `react`.

### Что даёт

-   Линтер больше не падает из-за отсутствующего плагина, и код соответствует ESLint-правилам проекта.
-   Подготовлены зависимости к будущему переходу на React 19: при обновлении React можно смело переезжать на `@react-three/fiber` 9.x.
-   Предупреждение про `unstable_act` зафиксировано: для полного снятия нужен React ≥ 19 или патч в `@react-three/fiber`; пока это не блокер, но стоит учесть в плане апгрейда.
